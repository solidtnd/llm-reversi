# 対戦ルール

## 盤面・基本ルール

- 8x8の標準的なリバーシ盤、初期配置も標準(中央4マスに石を斜め配置)。
- 黒(先手)・白(後手)が交互に着手する。
- 合法手が存在しない場合は自動的にパスする(LLMに問い合わせない)。
- 両者連続でパスした場合、終局とする。
- 盤面が埋まった場合も終局とする。
- 終局時、石数が多い方の勝ち。同数の場合は引き分け。

## 1手ごとの処理

1. 現在の盤面・合法手一覧をLLMに提示し、着手をJSON形式で応答させる。
2. 以下のいずれかの失敗が発生した場合、**原因(パース失敗/APIエラー)を問わず1手あたり通算1回だけ**再試行する(パース失敗用・APIエラー用に別々の予算を持つのではなく、1手につき1回のみという単一の予算)。既にこの1回を使い切った状態で(原因を問わず)再度失敗した場合は、その時点の理由でそのまま反則負けとする。
   - **パース失敗**(Adapterが`AdapterParseError`を送出): 再試行時は、直前の応答がなぜ失敗したか(パースエラーの内容)をプロンプトにフィードバックする(単純な同一プロンプトの再送はしない)。具体的には、直前の`AdapterParseError.message`を`request_move`の`retry_reason`引数にそのまま渡して再試行する([adapter-interface.md](adapter-interface.md#共通インターフェースイメージ)参照)。
   - **APIエラー**(レート制限・5xxエラー・ネットワークエラー等でAdapterが`AdapterAPIError`を送出): 再試行時は同一内容で再送する。
3. パース成功後、応答内容が合法手一覧に含まれない場合は反則負けとする(リトライしない)。この検証はAdapterの責務ではなく、呼び出し元(engine側)が行う([adapter-interface.md](adapter-interface.md#エラー通知)参照)。
4. 1手あたりの最大待ち時間(タイムアウト)を超えた場合も反則負けとする。タイムアウト秒数は**30秒**とする。この判定もAdapterではなく呼び出し元(engine側)が処理全体を時間で打ち切ることで行う(Adapterが自発的にタイムアウトを検知するわけではない)。
5. 反則負けとなった場合、理由(非合法手/タイムアウト/パース失敗/APIエラー)を区別して棋譜に記録する([../shared/log-schema.md](../shared/log-schema.md)の`forfeit_reason`に対応)。

### エラー種別とAdapterの例外設計

Adapterが送出する例外は`AdapterParseError`(パース失敗)・`AdapterAPIError`(APIエラー)の2種類のみとする([adapter-interface.md](adapter-interface.md#エラー通知)参照)。呼び出し元(engine)はこの例外の型を見て`forfeit_reason`を`parse_failure`/`api_error`のどちらにするか決定する。一方、`illegal_move`(合法手検証)と`timeout`(処理全体の予算超過)は、Adapterの例外ではなく**呼び出し元(engine)側のロジックで判定する**(前者は上記3、後者は上記4に対応)。

### タイムアウトの扱い

リトライを含めた処理全体が`timeout_seconds`の予算(30秒)を超えた場合は、原因がパース失敗・APIエラーのどちらであっても`timeout`として反則負けとする(タイムアウトは「1手あたりの処理全体の予算」という位置づけを保つため、原因の種類によらず予算超過は常に`timeout`とする)。予算超過時点でAdapter呼び出しが実行中の場合は、その呼び出し自体を呼び出し元が打ち切る。

エラーの詳細(例外メッセージ等)は、モデルの応答である`llm_raw_response`とは別に、`error_detail`フィールドに記録する([../shared/log-schema.md](../shared/log-schema.md)参照)。非合法手のような「モデル自身の応答内容が原因」の反則負けとは異なり、APIエラー・タイムアウトは基盤側の問題である可能性があるため、原因調査用に例外情報を残す。

- 反則負けとなった対局は「不成立」として除外するのではなく、**反則負けとして記録し集計に含める**(モデルの安定性を測る指標になるため)。
- 反則負けとなった対局の`result.score`(石数)は**記録しない(`null`とする)**。反則負けは石数の多寡ではなく反則行為そのもので決着しているため、スコアを記録すると「スコアで決着したかのように見える」誤解を招く。反則発生時点の実際の盤面は`moves`配列の最後の要素の`board_after`から常に参照できるため、情報が失われるわけではない([../shared/log-schema.md](../shared/log-schema.md)参照)。

既存のオセロ棋譜フォーマット(WTHOR/GGF)にはLLM対戦特有の反則負け・リトライという概念自体が存在しないため、これらの扱いは独自に設計する([../shared/log-schema.md#既存フォーマットとの関係](../shared/log-schema.md#既存フォーマットとの関係)参照)。

## 調整可能な値の管理方針

タイムアウト秒数や得点方式など、ルールとして固定ではなく運用上調整の余地がある値は、コードに埋め込まず**設定ファイルで管理する**([adapter-interface.md](adapter-interface.md)のモデル一覧設定ファイルと同様の方針)。

配置場所は`engine/league.yaml`とし、**`engine/models.yaml`(モデル一覧)とは別ファイルにする**。モデル一覧は新モデル登場のたびに末尾へ追記される「出場者名簿」であり、リーグ運営パラメータ(タイムアウト・得点方式)とは変更の理由・頻度が異なる別の関心事のため。ファイルを分けることで、「モデルを追加した」変更と「運営パラメータを変えた」変更のコミット・diffが混在しない(CLAUDE.mdの「`git log`自体を意思決定の履歴にする」方針と合う)。

```yaml
timeout_seconds: 30
concurrent_games: 4
points:
  win: 1
  draw: 0.5
  loss: 0
```

- `timeout_seconds`: 1手あたりの最大待ち時間(上記「1手ごとの処理」参照)。
- `concurrent_games`: リーグ実行時に同時進行させる対局数([engine-architecture.md](engine-architecture.md#並列実行)参照)。
- `points`: [../shared/metrics.md](../shared/metrics.md#ランキング指標)の勝点方式で使う重み。

## リーグ運営

- 出場モデルの全組み合わせで総当たり戦を行う。
- 同一カード(モデルA vs モデルB)は、先手後手を入れ替えて**2局**(先手・後手1回ずつ)対戦する。
- **モデル一覧(設定ファイル)への追加は差分実行できる。** 新しいモデルが登場して設定ファイルに追記した場合、実行済みのカードは再実行せず、新モデルと既存モデルとの未実施カードのみ実行する(例: モデルA/B/Cが総当たり済みの状態でモデルDを追加した場合、A-D・B-D・C-Dのみ実行し、A-Bなどは再実行しない)。実施済みかどうかは`data/results.jsonl`の各行の`black.id`/`white.id`から、対戦済みモデルの組み合わせを見て判定する([../shared/log-schema.md](../shared/log-schema.md#対局結果ログdataresultsjsonl)参照)。判定の粒度は**先手後手を区別した(黒id, 白id)の組**とする。カード=2局(先手・後手1回ずつ)なので、片方の向きだけログに存在する場合(実行途中で中断した等)は残りの向きだけが実行対象になり、取りこぼしが自然に補完される。

### 得点・ランキングの扱い

- 個々の対局の**勝敗(勝ち/負け/引き分け)は不変の事実として棋譜(`data/`)に記録する**。得点方式の選択によって変わることはない。
- 得点・ランキングは勝敗とは別に、集計時に得点方式(設定値)を適用して算出する。ランキングは**勝点方式**(勝ち=1点/引き分け=0.5点/負け=0点)と**Bradley-Terryモデルによる強さ推定**を併記する。ELOレーティングは、対局を処理する順序によって結果が変わってしまう(逐次更新のため)という性質が本プロジェクトの直感に合わないため不採用とした。詳細は[../shared/metrics.md](../shared/metrics.md#ランキング指標)を参照。
- 得点方式を事後に変更した場合でも、記録済みの勝敗データから**再計算できる**構成とする。
